## What the PR does

Fiado at the PDV creates a TAB sale. The sale, stock deduction, credit debit, cash receipt and audit are written in one transaction (`SaleRepository.commitSale`), with row locks on stock (fixed order) and on the customer, and a `FOR SHARE` check that the cash session is still open. The owner PIN is exactly 6 digits everywhere (D-02).

## Closed in this PR

- B1 and atomicity: sale, stock, debit, cash receipt and audit in one transaction.
- NI8: a sale is refused with 409 `CASH_SESSION_CLOSED` if the cash session closed meanwhile.
- Lock order and stock race: deterministic tests that hold the row lock from outside. Mutation-checked: removing the sort fails the lock-order test, removing `FOR UPDATE` fails the race test.
- I9: `create-sale.use-case.integration.test.ts` runs the use case with the real Drizzle repositories (cash sale, fiado within the limit, over the limit without and with the owner PIN).
- M4: products and stock are validated before an owner PIN attempt is consumed.
- N1/NB1/NI2/F1: one idempotency key per checkout, reused by the offline fallback; 409 carries `DUPLICATE_SALE` or `CASH_SESSION_CLOSED`; `settleOfflineSale` maps the offline queue by code, so a duplicate counts as synced, any other 409 stays in the queue, and only a network failure stops it. Mutation-checked.
- N2: any database error returns 500 without SQL text.
- Idempotency-Key longer than 128 characters returns 400.
- NI1: 6-digit owner PIN in registration, setup, sale, cancellation, PDV, management and login. No 4-digit PIN is in real use (owner, 2026-11-07), so no migration.
- Cleanups: shared `toAuditEventRow`, unused `auditPort` removed, stray block in `writeSale` removed, read methods use the injected database.

## Accepted, non-blocking

- NI3: the PDV idempotency key lives in memory. A page reload between a stored sale and the retry makes a new key. Documented in DECISIONS.md D-05.
- N9: `BcryptOwnerPinVerifier.matchOwnerPin` fallback reads the global `db`.
- M3: `CREDIT_SALE_LIMIT_AUTHORIZED` is audited from the read before the lock. The limit is re-checked under the customer lock, so no money is wrongly let through.
- A rejected queued sale (for example a closed cash session) stays in the queue and fails on every sync, with no user-facing way to resolve it.
- `findCurrentOpenSession` runs before the transaction (pre-existing on main); the in-transaction session check closes the money risk.
- `offline-sync.ts` treats 409 as synced; this is safe only because the sender maps non-duplicate 409 to 422, which the sender tests guard.
